# 智能底座产品需求文档

**版本**：v1.0 · **日期**：2026-09-29 · **状态**：评审稿
**工作名称**：智能底座（当前仓库产品：FreeLLM Gateway）

## 1. 产品概述

### 1.1 产品定位

智能底座是供 AI 应用、Agent、工作流和业务系统使用的统一 AI 能力平台，负责接入和管理模型 Provider，为上层提供统一 API，并逐步提供路由、用量治理、Agent 编排、知识与运行治理能力。首期从现有 FreeLLM Gateway 演进，优先跑通跨 Provider 的请求、故障切换和使用记录闭环。

### 1.2 问题与机会

团队接入多个模型供应商时，需要重复适配协议、分散维护 API Key，并自行处理模型不可用、速率限制、调用成本和运行记录。Provider 故障会直接影响上层业务；应用也难以回答一次请求经过哪个模型、是否切换、消耗多少资源。若再分别建设 Agent、工具和知识能力，会产生新的集成与治理成本。

智能底座将这些能力分阶段集中起来，让应用通过稳定的统一入口调用模型，并逐步把路由、配额、成本和上层 AI 能力纳入同一运行与治理体系。

### 1.3 目标用户

- **应用研发人员**：希望复用兼容接口接入不同模型，不在每个应用里重复实现 Provider 适配和故障处理。
- **平台管理员 / AI 运维人员**：负责 Provider 凭据、模型可用性、路由策略、调用记录及资源治理。
- **业务应用团队**：希望按应用和租户了解用量，并在后续阶段接入 Agent、Workflow 和企业知识。

首期重点服务自托管环境中的研发人员和平台管理员；企业多租户治理及 Agent 平台能力按路线图逐步建设。

## 2. 目标与成功标准

### 2.1 产品目标

1. 通过统一 API 调用多个已配置 Provider 的模型。
2. 当首选线路发生可切换故障时，底座可以按已配置顺序尝试备用线路并返回成功结果或清楚的最终错误。
3. 管理员和研发人员可以从调用记录中核对请求状态、所选 Provider/模型、耗时以及可获取的 Usage 信息。
4. Provider 凭据受到保护，管理界面、接口响应、导出内容和日志不会暴露明文密钥。
5. 以明确的阶段边界扩展到成本/租户治理和 Agent/知识编排，不把规划功能描述成已交付能力。

### 2.2 P0 验收指标

首期验收围绕一条可复现的端到端场景：配置至少两个可用 Provider/模型，通过统一入口发起请求；模拟首选线路的可切换故障后，备用线路成功响应；调用记录包含请求结果、实际线路和可获得的 Usage/耗时信息；凭据在展示和日志中均不可读。

具体成功率、延迟和容量目标须在目标部署环境建立基线后由产品与研发另行确认，本 PRD 不预设未经测量的 SLA 数值。

## 3. 范围与分期

### 3.1 能力边界与请求闭环

智能底座包含四类相互衔接的产品能力：Provider/模型目录负责“有哪些线路可用”；Gateway 与路由负责“如何安全地把请求交给合适线路”；Usage、请求记录与治理负责“调用结果如何核对和运营”；Agent、工具、知识和工作流负责“如何在统一运行层上组合更高阶能力”。P0 聚焦前三者中的最小模型调用闭环，P2 再加入 Agent OS 能力。

```text
应用 / 开发者
  → 统一 API 与调用方身份检查
  → 请求校验、模型能力匹配、健康候选筛选
  → 按已配置顺序调用 Provider
  → 可切换故障时尝试备用线路
  → 返回统一结果或可诊断的最终错误
  → 关联记录每次尝试、最终线路与可用 Usage
```

P0 中凭据保护覆盖 Provider Key 和 Gateway 现有调用认证；租户级独立 Key 与细粒度身份/配额属于 P1。任何失败切换都必须有界，且只针对明确可重试的错误类型；日志只保留可诊断且脱敏的信息。

### 3.2 分期范围

### P0：统一调用与可恢复的请求闭环

- Provider 与模型连接管理，包括凭据配置、模型发现/录入、健康探测和启停。
- 面向应用的统一模型调用入口，优先保持 OpenAI 兼容使用体验。
- 基础路由：按已配置顺序、能力匹配与健康状态选择线路。
- 基础 Fallback：对明确可重试的线路故障尝试备用线路；不对所有业务错误盲目重试。
- 请求 Usage / 调用记录：展示实际使用线路、状态、耗时及上游返回的 Token 信息（若上游提供）。
- 凭据加密保存、脱敏展示，并防止写入日志、普通导出和接口响应。
- 管理台首页提供运行状态、Provider 健康和待处理错误的入口。

### P1：多租户运营与高级路由

- Tenant、应用和面向调用方的独立 API Key 生命周期与权限范围。
- Token、请求数和费用配额；按日/月的使用限制和额度提醒。
- Provider、模型、租户、应用和 API Key 维度的 Usage 与成本视图。
- 质量、成本、延迟、稳定性和区域等高级路由偏好及可解释的选择原因。
- 运营告警、错误聚合和更完整的 Trace 检索。

### P2：Agent 与知识工作流平台

- Agent、Tools、Skills、Workflow、Knowledge 与 Memory 管理和运行。
- 多 Agent 协作、人工审核、权限隔离和运行记录。
- Prompt 版本管理、模型/Agent/Workflow 评测，并在治理策略确认后为路由提供评测信号。

## 4. 用户故事与验收标准

### P0 — 统一接入

**作为应用研发人员，我希望通过一个兼容入口调用不同 Provider 的模型，以便更换上游时无需在业务应用重复实现供应商协议。**

- [ ] 使用已授权凭据与已配置模型时，请求返回符合统一接口契约的结果。
- [ ] 未配置模型、无效凭据或请求格式错误时，返回可识别的错误，不泄漏上游密钥或内部堆栈。
- [ ] 流式/非流式、工具调用和其他兼容能力按产品支持矩阵明确标注；未支持能力须返回可诊断结果。

### P0 — 基础路由与 Fallback

**作为平台管理员，我希望配置模型候选线路并在可恢复故障时自动切换，以便单个 Provider 异常不立即中断业务请求。**

- [ ] 请求只会选择已启用、健康且满足所需能力的候选线路。
- [ ] 首选线路遇到配置为可切换的超时、速率限制或上游可恢复错误时，按候选顺序尝试备用线路。
- [ ] 鉴权失败、参数错误等不应通过重复调用同一请求来掩盖配置问题；是否切换由明确策略决定。
- [ ] 成功响应时记录最终使用的 Provider/模型及是否发生切换。
- [ ] 若发生切换，关联记录保留每次候选尝试的顺序、耗时和脱敏错误类别；授权管理员能从该请求的记录查看，不保存未脱敏的上游响应正文或凭据。
- [ ] 管理台提供请求详情视图，能按顺序查看该请求的主备尝试、结果和切换原因；基础列表继续显示最终状态与线路。
- [ ] 所有候选均失败时返回稳定、可诊断的统一错误，并保留各线路失败原因供授权管理员排查。

### P0 — Usage 与调用记录

**作为研发人员或平台管理员，我希望查看每次请求的结果和线路选择，以便核对调用是否成功并定位故障。**

- [ ] 每次已进入 Gateway 的请求都能关联到唯一记录或 Trace 标识。
- [ ] 记录包含时间、请求结果、模型/Provider、耗时，以及上游可提供的 Token 使用信息。
- [ ] 若上游未提供 Token 或价格数据，界面明确显示“不可用/未估算”，不伪造用量或费用。
- [ ] 按权限查询记录；日志内容不包含 Provider Key、调用方 Key 或未经脱敏的敏感内容。

### P0 — Provider 与密钥安全

**作为平台管理员，我希望安全地维护 Provider 凭据，以便集中管理上游连接而不扩大密钥泄露风险。**

- [ ] 创建、更新、禁用 Provider 凭据后，连接测试/模型发现使用最新的有效配置。
- [ ] 页面只显示脱敏后的凭据状态，不回显已保存的明文密钥。
- [ ] API 响应、错误日志、导出和审计记录不包含明文密钥。
- [ ] 无凭据或凭据无效时，状态和后续处理指引清晰。

### P1 — 租户、配额与成本

- [ ] 调用方 Key 可绑定租户/应用、有效期、允许模型和额度。
- [ ] 配额检查发生在模型请求之前；不足时拒绝调用并说明超限范围。
- [ ] 用量与成本可以按租户、应用、Key、Provider、模型和时间筛选。
- [ ] 未知模型价格、缺失 Token Usage 或不可估算请求明确标识，费用不得伪装为精确值。

### P1 — 高级路由与运营

- [ ] 管理员可以选择成本、延迟、质量、稳定性或区域偏好，并可查看选择原因。
- [ ] 不满足所选约束时，系统说明无候选原因或按管理员配置的降级策略处理。
- [ ] 速率限制、健康异常、费用/配额阈值触发可配置告警，重复告警有聚合或抑制规则。

### P2 — Agent、工具、知识与工作流

- [ ] Agent 可绑定模型、工具、技能、知识和权限；发布前可测试，发布后可禁用/回滚。
- [ ] 工具调用按授权范围和超时约束执行，失败时能在运行记录中定位节点。
- [ ] Workflow 支持条件、并行、循环和人工审核节点；运行状态和失败位置可查询。
- [ ] Knowledge 与 Memory 的数据来源、访问范围、生命周期和删除行为清晰可见。
- [ ] 评测数据集、指标和版本可以重复运行并比较，不以单次结果自动更改生产策略。

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| 兼容性 | 对外明确列出支持的接口、请求参数、流式与多模态能力；只承诺通过验证的能力。 |
| 安全 | 凭据加密存储、传输使用 TLS（本地开发环境除外）、密钥脱敏；管理与调用方权限分离。 |
| 隐私 | 请求正文、知识文件及工具结果按数据最小化原则记录；日志保留策略可配置并遵守部署方要求。 |
| 可靠性 | 限制重试次数和总请求时长；错误分类后才执行 Fallback，避免重复扣费或重放非幂等操作。 |
| 可观测性 | 记录请求关联标识、最终线路、状态、耗时、Usage 可用性和错误类别。 |
| 部署 | 首期支持自托管单实例路径；任何多副本能力必须明确共享状态和一致性要求后再承诺。 |
| 可用性 | 主要管理操作提供明确的成功、失败、加载和空状态；危险操作需说明作用对象。 |
| 国际化 | 延续当前管理台的中英文能力；产品文档首版以中文为主。 |

## 6. 超出范围

- P0 不承诺 Agent、Tools、Skills、Workflow、Knowledge 或 Memory 的生产级运行。
- P0 不承诺企业级 SSO、完整 RBAC、跨组织隔离或多实例高可用。
- P0 不承诺供应商真实余额/额度读取；只有 Provider 提供可靠接口时才显示其数据。
- 不自动选择或切换用户账号来规避 Provider 限额、计费或服务条款。
- 不宣称未经测量的 99.9% 可用率、固定 P95 延迟或成本节省比例。

## 7. 当前实现状态（基于仓库核对）

| 能力 | 当前状态 | 说明 |
|---|---|---|
| Provider/模型管理、发现与探测 | 已有 | 管理台支持 Provider、连接和模型路由维护。 |
| 统一模型 API | 已有 | 当前提供 OpenAI 兼容模型、聊天和生图入口；其他 API 形态须按支持矩阵确认。 |
| 基础能力路由与 Fallback | 已有 | 当前有能力/优先级/健康状态和失败切换逻辑；策略范围小于完整智能路由愿景。 |
| Provider Secret 保护 | 已有 | 本地系统凭据存储/云端加密存储；调用方独立 Key 生命周期不是同一能力。 |
| Usage、配额、Tenant/App | 部分具备 | 有用量和额度视图及 Tenant/App 数据；完整独立调用方 Key、硬额度及成本治理仍需按验收项核对。 |
| 健康、连接记录、审计与 Trace | 部分具备 | 有健康和连接/使用记录，后端尝试可通过 request_id 关联；管理台尚无统一的请求尝试时间线，错误聚合和治理审计未覆盖。 |
| Agent、Tools、Skills、Workflow、Knowledge、Memory | 规划中 | 当前仓库没有可供本 PRD 宣称已交付的完整模块。 |

## 8. 风险与待决策

| 风险/待决策 | 影响 | 建议处理 |
|---|---|---|
| Provider 的错误语义、重试安全和幂等性不一致 | Fallback 可能造成重复请求或重复费用 | 建立错误分类与 Provider 适配器契约；只对明确可重试错误切换。 |
| Usage、价格和模型能力元数据不完整 | 成本与路由评分可能不准确 | 区分实测、上游报告和估算数据，并显示数据来源与置信状态。 |
| Tenant/App 与调用方身份边界尚未统一 | 配额和数据隔离无法可靠验收 | P1 前明确调用方 Key、身份验证、租户归属与管理员权限模型。 |
| 自托管与多租户平台的产品边界 | 单机默认与企业部署要求可能冲突 | P0 以自托管/单实例为基线；多副本与企业隔离单独评估。 |
| “智能底座”与 FreeLLM Gateway 的品牌关系 | 文案、导航和升级路径不一致 | 当前文档采用“智能底座（基于 FreeLLM Gateway）”工作名称，品牌是否改名待产品确认。 |

## 9. 验收与测试策略

- P0 必须通过 Provider 配置、统一 API 调用、模拟主线路故障并由备用线路成功、Usage/记录核对、密钥不泄漏这条端到端验收。
- 管理台首页必须正确显示已配置的运行状态、健康信号和待处理异常；空数据与数据不可用状态必须可区分。
- 单元测试覆盖错误分类、候选筛选、Fallback 次数边界、凭据脱敏和配额/Usage 计算。
- 集成测试使用可控 Mock Provider，不要求 CI 持有真实供应商凭据。
- 人工验收覆盖管理台连接配置、状态/错误反馈、记录筛选和部署后健康检查。
- 测试用例与功能成熟度标记见 [智能底座测试计划](../testing/SMART_BASE_TEST_PLAN.md)。
